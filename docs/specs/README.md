## Reading Order

1. Start with [Vision](./vision.md) for product intent and scope.
2. Continue with [Requirements](./requirements.md) for functional and non-functional expectations.
3. Use [User Stories](./user-stories.md) and [Acceptance Criteria](./acceptance-criteria.md) for implementation-facing behavior.
4. Use [Runtime Contract](./runtime-contract.md) for supported inputs, outputs, diagnostics, validation, and module boundaries.
5. Use [Acceptance Suite](./acceptance-suite.md) for permanent fixture structure, benchmark tiers, and regression policy.
6. Use [Pipeline Modules](./pipeline-modules.md) for stage boundaries, data flow, and implementation slices.
7. Use [Technical Spec](./technical-spec.md) for architecture and tooling direction.
8. Use [Phases](./phases.md) for the fixed implementation roadmap and completion criteria.
9. Use [Delivery Plan](./delivery-plan.md) for execution order and governance.
10. Use [Lessons Learned](../lessons-learned.md) for archived prototype evidence and reconstruction notes.

## Notes

- The current stack recommendation is provisional, not locked.
- The project is browser-first and local-first.
- Specs should evolve with benchmark evidence.
- Benchmark-backed technical decisions must be preserved, not only the latest recommendation.
